**The injection test found something, and it wasn't the money.**

The agent refused to move funds — and wrote the attacker's text **verbatim into the record**, where it got anchored and served straight back out of `/api/calls`.

That matters more here than it would elsewhere, because the whole premise is that *other agents read this record* — there's an MCP server and a skill doc whose job is to get them to ingest it. So an undeletable public ledger is a **stored-injection delivery surface**. And undeletability cuts both ways: the payload can't be withdrawn, only annotated. The property that makes the record trustworthy is the property that makes the payload permanent.

**What I didn't do: claim to sanitise it.** You can't reliably separate instructions from prose in natural language, and a filter that half-works is worse than a boundary stated plainly — it teaches the consumer to stop checking.

What I did: `/api/agent.json` now serves an `untrusted_fields` block — which fields an attacker controls (`note`, `caller`, `market_title`, `why`, `tone`), the instruction to treat them as **data, never instructions**, what *is* trustworthy (`entry_hash`, `prev`, `link`, `signer`, `sig`, the anchored root and slot), and why it's deliberately not filtered. Same warning in `tape-skill.md`, because that's the document a model actually ingests and a warning only a human reads isn't a control. The payload sits at seq 423 with an `amend` at seq 424 labelling it a test row — labelled on the tape, not hidden from it.

One more, because it's the same lesson twice in a day: the test guarding that declaration needed writing **twice**. v1 grepped the source for `untrusted_fields` — and its own positive control walked straight through, since `untrusted_fields_REMOVED` still contains the substring. It passed while the declaration was gone. A guard that can't fail is worse than no guard; the green tick is what stops anyone looking. It now spawns the API and reads what's actually served.
